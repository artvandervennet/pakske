# Friends: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Two people become friends once (a request from a list, or a friend link that works once), and each chooses per friend which of their own lists that friend finds on their Lists page.

**Architecture:** Friends are their own part beside lists: four new tables and one new domain file. Lists, links and `getListView` are untouched; a friend who opens a list is a buyer like anyone with the link. A list shown to a friend is only a row that puts it on their Lists page.

**Tech Stack:** Nuxt 4, Vue 3, drizzle-orm on better-sqlite3, zod, vitest, @nuxtjs/i18n, the Gesso components.

**Spec:** `docs/superpowers/specs/2026-11-19-friends-design.md` (step 3 of its "Order of work"; "send to a friend" is the next plan). Its section "The rules" binds every task here.

## Global Constraints

- No directory: a request needs a list the sender can open; a friend link needs its token. No route takes a name or an email address.
- Nobody sees anyone else's friends. No answer holds a friend of someone other than the asker.
- A friend sees a name and the lists ticked for them. No email address, no other lists, not who else sees a list.
- `server/domain/friends.ts` never reads purchases or notes; a source test pins that. `getListView` does not change.
- An owner never learns who opened a list. Showing a list reports nothing back; hiding a shown list tells its owner nothing.
- Declining is silent: to the sender a declined request looks and behaves like a waiting one.
- Caps, exactly: `MAX_FRIENDS = 100`, `MAX_WAITING_REQUESTS = 20` (per sender, counting every request the sender still sees), `MAX_OPEN_FRIEND_LINKS = 10` (a new one drops the oldest), `FRIEND_LINK_DAYS = 30`.
- Every sentence in `i18n/locales/nl.json` and `en.json`, same keys in the same order, round quotes only.
- Logged-in checks: a git worktree, the Firebase stand-in, `nuxt dev --port 3112`. Never port 3400, never a second `nuxt dev` in the main checkout.
- One commit per task, ending with `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`. Nothing is pushed.

## Review Focus

1. **Two people ask each other.** Whichever request lands second makes them friends; one friendship row, no request left, each side told once. (Task 1 test.)
2. **Friends again after unfriending.** Nothing either showed the other before comes back. (Task 3 test.)
3. **A friend becomes co-owner of a list shown to them.** It is under their own lists, not also under "Van vrienden"; when they leave the list it is shown again only while a remaining owner still ticks it. (Task 3 test.)
4. **A request whose list is gone before it is answered** (deleted, new link, sender no longer able to open it). It can still be accepted or declined; "via" is left out. (Task 1 test.)
5. **Two friends with the same name.** Every tick, row and request goes by id; the page shows both. (Task 3 test and Task 6 check.)

```ts
// schema

// errors: 'friend_limit' 409, 'request_limit' 409, 'not_friends' 404
// NoticeKind += 'friend_accepted'
// friends.ts
export const MAX_FRIENDS = 100
export const MAX_WAITING_REQUESTS = 20
export function areFriends(db: Db, a: number, b: number): boolean
export function askFriend(db: Db, userId: number, listToken: string, ownerId: number): 'asked' | 'friends'
export function answerRequest(db: Db, userId: number, requestId: string, accept: boolean): { friendId: number } | null
export function withdrawRequest(db: Db, userId: number, requestId: string): void
export interface RequestsView {
  incoming: { id: string, fromId: number, from: string, via: string | null, fresh: boolean }[]
  outgoing: { id: string, toId: number, to: string }[]
}
export function listRequests(db: Db, userId: number): RequestsView
export function countFreshRequests(db: Db, userId: number): number
export function markRequestsSeen(db: Db, userId: number): void
export function removeFriend(db: Db, userId: number, friendId: number): void
```

Rules the tests pin:

- `askFriend`: the list is live and `ownerId` owns it, else `not_found`; asking yourself is `forbidden`; already friends answers `'friends'` and changes nothing. A row of the sender's own for that person (waiting, declined or hidden) is un-hidden and answers `'asked'` without touching anything else. A row the other way, waiting or declined, makes them friends: both rows go, and the earlier sender gets a `friend_accepted` notice. Otherwise a waiting row with `listId`, unless the sender already sees 20 (`request_limit`).
- Becoming friends, by any way: `friend_limit` when either side has 100.
- `answerRequest`: only the receiver, only while waiting; anything else `not_found`. Accept: friendship, the row goes, the sender gets `friend_accepted`, returns the new friend. Decline: status `declined`, returns null, no notice.
- `withdrawRequest`: only the sender. Waiting: the row goes. Declined: `hidden` is set and the row stays.
- `listRequests`: incoming are waiting ones only, newest first, `via` the list's title or null; outgoing are the sender's rows that aren't hidden, declined ones included and indistinguishable.
- `removeFriend`: the friendship goes, silently; `not_friends` when there is none.
- A notice for friends has `title: ''`, no wish, no list; `listNotices` gives it `token: null`.

```ts
export const FRIEND_LINK_DAYS = 30
```

Rules: the token comes from `newListToken`. `closed` is used or past `expiresAt`; `own` for its maker; `friends` when the two are friends already (the link is left unused). ### Task 3: Showing lists to a friend

**Files:** Modify `server/db/schema.ts` (+ migration), `server/domain/friends.ts`, `server/domain/lists.ts` (`leaveList`, `deleteList`), `server/domain/visits.ts`, `server/domain/notices.ts`, `shared/schemas/list.ts`; Test `test/friends.test.ts`, `test/visits.test.ts`, `test/delete-account.test.ts`

**Interfaces (produced):**

```ts
listFriends(listId → lists cascade, userId → users cascade, shownBy → users cascade, addedAt, hiddenAt null)
            // PK (listId, userId, shownBy), index on userId
// NoticeKind += 'list_shown'
export interface FriendView {
  id: number
  name: string
  /** Every live list of the asker's own, with whether this friend is shown it. */
  shows: { token: string, title: string, shown: boolean }[]
  /** The lists this friend shows the asker, hidden ones left out. */
  sees: { token: string, title: string }[]
}
export function listFriends(db: Db, userId: number): FriendView[]                       // by name, then id
export function setShownLists(db: Db, ownerId: number, friendId: number, listTokens: string[]): void
export function listFriendsForList(db: Db, ownerId: number, listToken: string): { id: number, name: string, shown: boolean }[]
export function setShownTo(db: Db, ownerId: number, listToken: string, friendIds: number[]): void
export interface ShownList { token: string, title: string, owners: string[], by: string[] }   // in shared/schemas/list.ts
export function listShownLists(db: Db, userId: number): ShownList[]                     // newest tick first
export function hideShownList(db: Db, userId: number, listToken: string): void
export function isShownTo(db: Db, userId: number, listId: number): boolean
```

Rules: both setters replace this owner's ticks only (another owner's rows for the same friend stay). A token that isn't a live list of the owner's is `not_found`; an id that isn't a friend is `not_friends`. A friend who owns the list gets no row. A new tick leaves the friend a `list_shown` notice (title: the list's, `listId`); an untick deletes the row and that notice and says nothing. A friend sees a list while some row for them isn't hidden, the list is live, its `shownBy` still owns it and the two are still friends; never a list they own. `hideShownList` sets `hiddenAt` on every row of that list for the person; ticking again after an untick shows it again. `removeFriend` now also deletes both directions' rows and `list_shown` notices. `leaveList` deletes the leaver's rows for that list, `deleteList` every row for it; `lists.ts` uses the table directly and keeps reading neither purchases nor notes. `listOpenedLists` leaves out lists that `isShownTo` the person. `listNotices` gives a `list_shown` notice the list's token while it is still shown to its receiver, else null.
